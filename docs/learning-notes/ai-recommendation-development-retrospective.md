# LinguaRoute AI 추천·통합 개발 상세 정리

> 기록 범위: 2026-08-11까지의 개인 개발·검증 회고입니다. 현재 구현 상태와 충돌할 경우 최신 `dev`의 코드, 테스트, `docs/mvp-checklist.md`, `docs/mvp-verification.md`를 우선합니다.

> 작성 목적: AI 추천 담당자 담당 기능을 팀원과 발표자에게 정확히 전달하고, 발표 준비와 개인과제 작성에 재사용하기 위한 상세 문서

---

## 1. 문서 결론

AI 추천 담당자이 담당한 **AI 추천·통합의 핵심 개발 범위는 완료**했다.

단순히 OpenAI API를 호출한 것이 아니라, 직원 권한 확인부터 수강 이력 조회, 실제 강의 후보 조회, AI 추천, 결과 재검증, DB 저장, 프론트 화면 출력까지 하나의 MSA 흐름으로 연결했다. 직원 OAuth 로그인부터 실제 OpenAI 추천 결과 확인과 MariaDB 저장까지 브라우저 종단 간 시연도 완료했다.

다만 다음 작업은 별도로 구분해야 한다.

- 기능 개발: 완료
- 실제 OpenAI 및 통합 시연: 완료
- 로컬 변경사항의 커밋·푸시·PR: 미완료
- 검증 문서의 최신 결과 반영: 일부 미완료
- 실제 토큰 스트리밍, 사용량 제한 등 운영 고도화: 선택 사항

따라서 발표에서는 “AI 추천 기능을 아직 설계 중”이라고 말할 필요는 없다. 다만 로컬에 남아 있는 변경사항이 원격 저장소에 전달되기 전까지는 “팀 저장소 반영까지 완료했다”고 표현하면 안 된다.

## 2. 담당 역할과 경계

| 담당자 | 담당 영역 | 담당 서비스 | 주요 역할 |
| --- | --- | --- | --- |
| AI 추천 담당자 | AI 추천·통합 | `recommend-service` | AI 추천, Gateway 연동, 서비스 통합, 프론트 추천 API 연결, 통합 테스트 |

### 2.1 직접 개발한 부분

- FastAPI 기반 `recommend-service`
- 추천 요청·응답 모델
- OpenAI Provider와 로컬 Provider
- 추천 서비스의 핵심 처리 로직
- 추천 결과 검증 및 규칙 기반 fallback
- 추천 요청과 추천 항목 저장 구조
- user/course/enrollment 내부 API를 호출하는 클라이언트
- Gateway 추천 라우팅 및 내부 경로 외부 차단 구성
- Vue 추천 화면의 실제 API 연동
- 추천 관련 자동 테스트와 통합 검증
- 개발·API·보안 관련 문서

### 2.2 다른 팀원의 구현과 구분해야 하는 부분

`user-service`, `course-service`, `enrollment-service`의 도메인 기능 자체는 각 서비스 담당자의 구현이다. AI 추천 담당자의 역할은 이 서비스들이 제공하는 내부 API 계약을 확인하고 `recommend-service`에서 올바르게 소비하도록 연결한 것이다.

발표에서는 다음처럼 표현하는 것이 정확하다.

> user-service, course-service, enrollment-service 담당자와 내부 API 계약을 맞추고, recommend-service에서 사용자 권한·수강 이력·강의 후보를 조회하도록 통합했습니다.

다음 표현은 피한다.

> 제가 user-service의 사용자 관리와 course-service의 강의 조회를 모두 구현했습니다.

## 3. 서비스를 만든 이유

### 3.1 사용자가 겪는 문제

기업 외국어교육 플랫폼에 강의가 많아지면 직원은 자신의 업무에 어떤 강의가 필요한지 판단하기 어렵다. 단순한 언어·난이도 필터만으로는 다음과 같은 상황을 충분히 반영하기 어렵다.

- 어떤 직무에서 사용할 것인지
- 고객 미팅, 발표, 협업, 출장 중 어떤 상황인지
- 현재 언어 수준이 어느 정도인지
- 이번 학습을 통해 무엇을 할 수 있게 되고 싶은지
- 이미 듣고 있거나 수강한 강의가 무엇인지

### 3.2 AI 추천이 제공하는 가치

직원이 언어, 수준, 직무, 상황과 목표를 입력하면 AI가 실제 등록된 강의 후보 안에서 적합한 강의를 고르고 이유를 설명한다. 사용자는 전체 강의 목록을 하나씩 비교하지 않아도 되고, 기업은 직원이 업무 목적에 맞는 강의를 빠르게 찾도록 도울 수 있다.

### 3.3 AI만 호출하면 해결되지 않는 이유

LLM은 자연스러운 설명을 잘 작성하지만 다음 문제가 있다.

- 플랫폼에 존재하지 않는 강의를 만들어낼 수 있다.
- 이미 수강 중인 강의를 다시 추천할 수 있다.
- 비활성화된 강의를 추천할 수 있다.
- 요청한 언어와 다른 강의를 추천할 수 있다.
- 외부 API 장애나 비용 제한으로 호출에 실패할 수 있다.

따라서 이 기능의 핵심은 “OpenAI에 질문하기”가 아니라, **MSA의 실제 데이터와 외부 AI를 안전하게 결합하는 구조**를 만드는 것이었다.

## 4. 초보자를 위한 핵심 용어

| 용어 | 쉬운 설명 | 이 프로젝트에서의 의미 |
| --- | --- | --- |
| MSA | 기능별로 서버를 나누어 개발하는 구조 | 사용자, 강의, 수강, 결제, 추천을 서로 다른 서비스가 담당 |
| API Gateway | 외부 요청이 처음 들어오는 공통 입구 | 로그인 토큰 확인 후 요청을 적절한 서비스로 전달 |
| OAuth2 | 로그인 후 Access Token을 발급받는 표준 절차 | 직원 로그인 후 보호된 추천 API 호출에 사용 |
| Access Token | 로그인한 사용자를 증명하는 임시 인증 문자열 | Gateway가 사용자를 확인하고 `X-User-Id`를 전달할 때 사용 |
| Provider | 외부 AI 사용 방식을 감싸는 교체 가능한 구성요소 | OpenAI Provider와 로컬 Provider를 분리 |
| enum | 허용 가능한 값을 미리 제한한 타입 | 언어·수준·업무 상황에 잘못된 문자열이 들어오는 것을 차단 |
| fallback | 주 기능이 실패했을 때 사용하는 대체 방법 | OpenAI 장애 시 규칙 기반 추천 반환 |
| SSE | 서버가 응답을 여러 조각으로 나누어 실시간 전송하는 방식 | 향후 실제 토큰 스트리밍 UI에 사용할 수 있음 |
| 내부 API | 서비스끼리만 사용하는 API | 추천 서비스가 사용자·강의·수강 정보를 조회할 때 사용 |
| 구조화 출력 | LLM이 정해진 JSON 구조로 응답하도록 제한하는 방식 | 추천 강의 ID와 이유를 안정적으로 파싱하기 위해 사용 |

## 5. 전체 시스템 구조

```text
[Vue Frontend]
      │
      │ Authorization: Bearer Access Token
      ▼
[API Gateway]
      │
      │ 인증 사용자 ID 전달
      ▼
[recommend-service]
      ├── user-service
      │     └── 사용자 회사·업무 권한·상태 확인
      ├── enrollment-service
      │     └── 기존 수강 이력 확인
      ├── course-service
      │     └── 실제 ACTIVE 강의 후보 조회
      ├── OpenAI API 또는 Local Provider
      │     └── 후보 중 추천 강의와 이유 생성
      └── MariaDB
            └── 추천 요청과 추천 결과 저장
```

### 5.1 정상 추천 처리 순서

```text
1. 직원이 언어·수준·직무·상황·목표 입력
2. 프론트가 POST /api/courses/recommendations 호출
3. Gateway가 Access Token 검증
4. Gateway가 인증된 사용자 ID를 추천 서비스에 전달
5. recommend-service가 user-service에서 최신 권한과 상태 조회
6. EMPLOYEE + ACTIVE가 아니면 추천 요청 거부
7. enrollment-service에서 기존 수강 강의 ID 조회
8. course-service에 기존 수강 ID를 excludeIds로 전달
9. course-service가 요청 언어와 일치하는 ACTIVE 강의 후보 반환
10. OpenAI가 후보 안에서 최대 3개 강의와 이유 생성
11. recommend-service가 AI 결과를 실제 후보와 다시 대조
12. 유효한 추천 결과를 MariaDB에 저장
13. 프론트가 추천 이유와 강의 카드를 출력
```

### 5.2 OpenAI 장애 시 처리 순서

```text
OpenAI 호출 실패 또는 유효한 추천 0개
→ recommend-service가 예외를 사용자에게 그대로 노출하지 않음
→ 언어·수준·상황을 이용한 규칙 기반 후보 선택
→ source=RULE_BASED_FALLBACK으로 응답
→ 프론트가 “규칙 기반 추천으로 전환” 안내 표시
```

## 6. recommend-service 내부 구조

### 6.1 Router

역할:

- 외부 추천 요청을 받는다.
- 필수 헤더와 요청 데이터를 확인한다.
- user-service에서 최신 사용자 컨텍스트를 조회한다.
- 직원이고 활성 상태인지 인가한다.
- 검증된 요청을 Service로 전달한다.

중요한 이유:

토큰에 들어 있는 정보만 믿으면 로그인 후 퇴사·비활성화된 사용자의 최신 상태가 반영되지 않을 수 있다. 그래서 추천 요청 시 user-service에서 최신 상태를 다시 조회한다.

### 6.2 Client

역할:

- `UserServiceClient`: 회사 ID, 업무 역할, 사용자 상태 조회
- `EnrollmentServiceClient`: 기존 수강 강의 ID 조회
- `CourseServiceClient`: 추천 가능한 실제 강의 후보 조회

중요한 이유:

추천 서비스가 다른 서비스의 DB를 직접 조회하지 않고 API 계약에만 의존하게 한다. 서비스의 URL, 헤더, 응답 구조 차이는 Client 경계에서 흡수한다.

### 6.3 Service

역할:

- 전체 추천 흐름 조정
- 기존 수강 강의 제외
- OpenAI 또는 로컬 Provider 호출
- AI 결과 재검증
- fallback 결정
- 추천 결과 저장

Service는 여러 기능을 직접 구현하기보다 각 구성요소가 올바른 순서로 동작하도록 조정한다.

### 6.4 Provider

역할:

- `OpenAiRecommendationProvider`: 실제 OpenAI Responses API 호출
- `LocalAiRecommendationProvider`: API 키가 없는 환경에서 로컬 추천 결과 생성
- Factory: 환경변수에 따라 사용할 Provider 선택

Provider를 분리한 이유:

- 자동 테스트에서 유료 API를 호출하지 않기 위해
- OpenAI 키가 없는 팀원 환경에서도 서비스를 실행하기 위해
- 향후 다른 AI 모델로 교체하기 쉽게 하기 위해
- 외부 장애가 핵심 서비스 로직에 직접 퍼지는 것을 막기 위해

### 6.5 Repository

역할:

- 추천 요청 저장
- 추천 강의 항목과 이유 저장
- 추천과 추천 항목의 내부 관계 관리

추천 서비스가 생성한 데이터는 추천 서비스가 소유한다. 사용자와 강의 ID는 다른 서비스의 논리적 식별자이므로, 다른 서비스 테이블을 가리키는 DB 외래키는 만들지 않았다.

## 7. 주요 기술 선택과 이유

### 7.1 자유 문자열 대신 enum을 사용한 이유

초기에는 언어, 수준과 상황을 문자열로 받을 수 있었다. 이 경우 `SPANISH`, `MASTER`, `ARCHIVED`처럼 course-service가 지원하지 않는 값도 추천 서비스 내부까지 들어올 수 있다.

선택:

- course-service와 동일한 enum 계약 적용
- 잘못된 요청은 외부 서비스 호출 전에 `422`로 거부

가치:

- 잘못된 요청을 초기에 발견
- 서비스 간 계약 변경이 테스트에서 바로 드러남
- 오타와 미지원 값으로 인한 통합 장애 감소

### 7.2 일반 강의 목록 API 대신 추천 전용 내부 API를 사용한 이유

일반 강의 목록 API는 화면 표시를 위한 페이지 응답이고 사용자 인증을 전제로 한다. 추천 서비스는 특정 언어의 ACTIVE 강의 배열이 필요하다.

검토한 방법:

1. 일반 목록 API의 페이지를 끝까지 순회
2. course-service DB를 직접 조회
3. 추천 목적의 내부 API 사용

최종 선택:

```http
GET /internal/courses/recommend?language=ENGLISH&excludeIds=...
```

선택 이유:

- ACTIVE와 언어 필터는 강의 데이터를 소유한 course-service가 판단해야 한다.
- 추천 서비스가 페이지 처리와 강의 상태 규칙까지 알 필요가 없다.
- 다른 서비스 DB를 직접 조회하지 않아 MSA 경계를 유지할 수 있다.

### 7.3 `id`를 `courseId`로 변환한 이유

course-service 응답은 `id`, 추천 도메인과 AI 응답은 `courseId`를 사용했다.

두 이름을 서비스 전체에서 혼용하면 다음 문제가 생긴다.

- 어떤 ID가 강의 ID인지 확인하기 어려워진다.
- AI 결과와 후보 강의를 비교하는 코드가 복잡해진다.
- 필드 누락을 놓칠 수 있다.

따라서 Course Client가 응답을 받는 한 지점에서만 `id → courseId`로 변환했다. 추천 서비스 내부에서는 `courseId`만 사용한다.

### 7.4 `role` 대신 `businessRole`을 사용한 이유

기존 `role`은 Auth Server와의 호환을 위한 `STUDENT`, `INSTRUCTOR` 값이다. 하지만 실제 서비스의 업무 권한은 다음과 같다.

```text
PLATFORM_ADMIN
COMPANY_ADMIN
EMPLOYEE
```

추천 기능은 직원 전용이므로 `businessRole=EMPLOYEE`를 검사해야 한다. 퇴사 또는 정지된 직원이 기존 토큰으로 계속 추천을 요청하지 못하도록 `status=ACTIVE`도 함께 확인한다.

### 7.5 OpenAI 구조화 출력을 사용한 이유

자유로운 문장으로만 응답받으면 추천 강의 ID와 이유를 안정적으로 분리하기 어렵다. 따라서 OpenAI가 정해진 데이터 구조에 맞춰 결과를 반환하도록 했다.

그럼에도 구조화 출력 자체를 완전한 신뢰 경계로 사용하지 않았다. 서버는 다음을 다시 검사한다.

- 후보 목록에 존재하는 강의 ID인지
- 같은 강의가 중복되지 않았는지
- 최대 추천 개수를 넘지 않았는지
- ACTIVE 강의인지
- 요청 언어와 일치하는지
- 추천 이유가 비어 있지 않은지

### 7.6 기본 모델을 Luna로 선택한 이유

추천 작업은 새로운 강의를 창작하는 작업이 아니라, 서버가 전달한 소수의 후보 안에서 적합한 항목을 선택하고 이유를 작성하는 제한된 작업이다.

비용·품질을 고려해 기본 모델을 비용 민감형 `gpt-5.6-luna`로 두고, `OPENAI_MODEL` 환경변수로 교체할 수 있게 했다.

### 7.7 fallback을 유지한 이유

외부 AI API는 다음 이유로 실패할 수 있다.

- API 키 누락 또는 만료
- 월 사용 한도 도달
- 네트워크 지연
- OpenAI 서비스 장애
- 응답 형식 불일치
- 유효한 추천 결과 부재

이때 추천 화면 전체가 오류로 끝나면 사용자는 아무 결과도 받지 못한다. 따라서 서버가 이미 확보한 실제 강의 후보를 이용해 규칙 기반 추천을 제공한다.

### 7.8 Gateway 차단과 내부 API 키를 함께 적용한 이유

Gateway의 `/api/courses/**` 라우트는 범위가 넓어서 `/api/courses/internal/**`까지 포함할 수 있었다.

Gateway 차단만 사용하면:

- 외부 경로는 막을 수 있지만 내부 네트워크에서 서비스 포트로 직접 호출하는 사용자를 구분하지 못한다.

내부 API 키만 사용하면:

- 인증은 검사할 수 있지만 내부 경로 자체가 외부 Gateway에 노출된다.

그래서 두 방식을 함께 사용했다.

```text
외부 요청 → Gateway에서 404
서비스 직접 호출 → X-Internal-Api-Key 검증
```

## 8. 트러블슈팅 사례

## 8.1 문서의 API와 실제 dev 코드가 달랐던 문제

### 문제 상황

초기 문서의 강의 API 경로와 응답 구조가 최신 `dev` 코드와 일부 달랐다. 문서만 따라 구현하면 추천 서비스 단위 코드는 작성할 수 있지만 실제 서비스 통합에서 실패할 수 있었다.

### 원인

여러 팀원이 동시에 개발하면서 코드와 문서 갱신 시점이 달라졌다. 일반 강의 목록 API와 추천 서비스에 필요한 후보 API의 목적도 달랐다.

### 검토한 대안

1. course-service 담당자에게 기존 API 전체를 문서에 맞춰 변경 요청
2. recommend-service가 실제 코드를 확인하고 경계에서 차이를 변환
3. 장기적으로 필요한 내부 API 계약을 팀과 재확정

### 선택

- 변경 비용이 작은 필드 차이는 추천 Client에서 변환
- 추천 후보 조회처럼 책임이 중요한 부분은 팀 내부 API 계약으로 확정

### 선택 이유

다른 서비스의 공개 API를 불필요하게 깨지 않으면서 추천 서비스가 실제 동작하는 계약을 사용할 수 있기 때문이다.

### 결과

- Course enum과 내부 API 경로를 실제 계약에 맞춤
- `id → courseId` 변환을 Client 경계에 격리
- 관련 계약 테스트로 재발 방지

### 발표용 한 문장

> 문서를 그대로 믿지 않고 실제 dev 코드와 담당자 계약을 대조했으며, 다른 서비스의 책임을 침범하지 않도록 추천 서비스 경계에서 차이를 변환했습니다.

## 8.2 `id`와 `courseId` 불일치 문제

### 문제 상황

course-service는 강의 식별자를 `id`로 반환했지만 추천 API와 AI 모델은 `courseId`를 사용했다.

### 원인

각 서비스가 자신의 도메인에 맞춰 DTO 이름을 설계하면서 동일한 개념의 필드명이 달라졌다.

### 잘못된 접근 가능성

- 서비스 전체에서 `id`와 `courseId`를 모두 허용
- 매번 조건문으로 두 필드 중 하나를 선택

이 방식은 코드 곳곳에 변환 로직이 퍼져 오류 가능성이 커진다.

### 해결

Course Client에서 응답을 받는 즉시 `id`를 `courseId`로 정규화했다.

### 결과

추천 서비스 내부에서는 항상 `courseId`만 사용하고, AI 결과와 후보 강의를 단순하게 비교할 수 있게 됐다.

---

## 8.3 `role`과 `businessRole` 혼동 문제

### 문제 상황

토큰과 사용자 데이터에 `role`과 `businessRole`이 함께 존재했다. `role=STUDENT`만 검사하면 플랫폼의 실제 직원 권한을 정확히 판단할 수 없다.

### 원인

기존 Auth Server의 호환 역할과 LinguaRoute의 업무 역할이 서로 다른 목적을 가졌다.

### 해결

- user-service 내부 API에서 최신 권한 컨텍스트 조회
- `businessRole=EMPLOYEE` 확인
- `status=ACTIVE` 확인

### 결과

기업 관리자나 플랫폼 관리자가 직원 추천 API를 사용하는 것을 막고, 비활성 직원도 즉시 차단할 수 있게 됐다.

### 발표용 한 문장

> 로그인 호환용 role과 실제 서비스 권한인 businessRole을 구분하고, 추천 시점의 최신 계정 상태까지 다시 확인했습니다.

---

## 8.4 `companyId`를 어디에서 얻을지 결정한 문제

### 문제 상황

추천 결과에는 사용자의 회사 정보가 필요하지만, 클라이언트가 보낸 `companyId`를 믿으면 다른 회사 ID를 위조할 수 있다.

### 검토한 대안

1. 프론트 요청에 `companyId` 포함
2. Gateway 헤더만 사용
3. user-service에서 사용자 ID를 기준으로 최신 회사 정보 조회

### 선택

user-service의 권한 컨텍스트 API에서 `companyId`를 조회했다.

### 이유

회사의 소속 정보는 user-service가 소유한다. 클라이언트 입력보다 데이터 소유 서비스의 최신 값을 사용하는 것이 안전하다.

## 8.5 AI가 없는 강의를 추천할 수 있는 문제

### 문제 상황

프롬프트에 후보 강의를 전달해도 LLM은 후보에 없는 ID나 중복 ID를 반환할 수 있다.

### 원인

LLM은 확률적으로 응답을 생성하므로 프롬프트 지시만으로 데이터 무결성을 보장할 수 없다.

### 해결

1. 구조화 출력으로 기본 형식을 제한
2. 서버에서 실제 후보 ID와 대조
3. 중복·비활성·언어 불일치·빈 이유 제거
4. 유효 결과가 없으면 fallback

### 결과

자연어 생성은 AI에 맡기되 최종 데이터의 신뢰 여부는 서버가 판단하는 구조가 됐다.

### 발표용 한 문장

> LLM 응답은 신뢰할 수 없는 외부 입력으로 취급하고, 실제 ACTIVE 강의와 다시 대조한 뒤 사용자에게 반환했습니다.

## 8.6 OpenAI API 키와 비용 문제

### 문제 상황

팀원 모두가 유료 API 키를 가지고 있지 않고, 자동 테스트에서 실제 OpenAI를 호출하면 반복적으로 비용이 발생한다.

### 해결

- `OPENAI_API_KEY`가 있으면 실제 OpenAI Provider 사용
- 키가 없으면 Local Provider 사용
- 자동 테스트에서는 가짜 Provider 응답 사용
- 실제 과금 테스트는 승인된 수동 시연에서만 실행
- 월 사용 한도를 낮게 설정하고 hard limit 적용

### 결과

개발·자동 테스트와 실제 AI 검증을 분리해 비용을 통제하면서도 실제 OpenAI 연동을 증명할 수 있었다.

## 8.7 Auth Web Client Secret 문제

### 문제 상황

브라우저 OAuth 로그인에서 Authorization Code를 Access Token으로 바꾸려면 web-client secret이 필요했다. 처음에는 팀원에게 별도 비밀값을 받아야 하는 것으로 이해했다.

### 원인

Auth Server의 클라이언트 등록값과 user-service 환경변수 관계가 명확하지 않았다.

### 해결

최신 `dev`의 Compose 구성을 확인한 결과, 교수님 제공 `msa-lecture/auth-server:1.0` 이미지에서는 로컬 실습용 기본값이 다음과 같이 자동 주입됐다.

```text
AUTH_WEB_CLIENT_SECRET=${AUTH_WEB_CLIENT_SECRET:-[개발용 기본값]}
```

따라서 임의의 secret을 새로 만들거나 알아낼 필요 없이 최신 Compose로 user-service를 재빌드했다.

### 결과

브라우저 로그인 후 `/callback`에서 Code 교환이 성공하고 직원 홈으로 이동했다.

## 8.8 “Access Token이 만료되었습니다” 메시지 문제

### 문제 상황

로그인 화면에 Access Token 만료 안내가 나타나 새 로그인도 실패한 것처럼 보였다.

### 원인

브라우저 `sessionStorage`에 이전 실행의 만료된 토큰이 남아 있었다. 로그를 확인했을 때 새 로그인 흐름은 아직 `/login` 단계였고 Code 교환 실패 기록은 없었다.

### 해결

- 브라우저의 `sessionStorage` 정리
- 로그인 흐름 재시작
- `/callback`과 `/app` 이동 확인

### 결과

새 OAuth 로그인과 Access Token 발급이 정상 동작했다.

### 배운 점

화면의 오류 문구만 보고 서버 문제라고 단정하지 않고, 브라우저 상태·Gateway 로그·user-service 로그를 단계별로 확인해야 한다.

## 8.9 Gateway의 넓은 라우트가 내부 API를 노출한 문제

### 문제 상황

일반 강의 라우트 `/api/courses/**`가 `/api/courses/internal/**`까지 포함해 내부 API가 외부 Gateway를 통해 전달될 가능성이 있었다.

### 원인

경로 패턴이 넓고, 세부 차단 라우트보다 먼저 평가될 수 있었다.

### 검토한 대안

1. 내부 API 키만 적용
2. Gateway 경로 차단만 적용
3. Gateway 차단과 내부 키 검증을 함께 적용
4. 서비스용 OAuth Client Credentials 도입

### 선택

MVP 범위에서는 우선순위가 높은 차단 라우트와 내부 API 키를 함께 적용했다.

### 결과

```text
Gateway 내부 경로 접근 → 404
서비스 직접 호출, 키 없음·오류 → 401
서비스 직접 호출, 정상 키 → 200
```

### 발표용 한 문장

> 외부에서는 내부 경로 자체를 숨기고, 내부에서 직접 호출하더라도 서비스 키를 검사하는 이중 방어를 적용했습니다.

## 8.10 최신 dev 병합과 Docker 재빌드 문제

### 문제 상황

최신 `dev`에는 OAuth 기본값과 ARM64 오프라인 실행 구성이 추가됐다. 기존 추천 브랜치에는 프론트와 문서의 미커밋 변경사항도 있어 단순 브랜치 전환 시 손실 위험이 있었다.

### 해결

- 미커밋 변경사항을 보존
- 최신 `dev`를 기능 브랜치에 병합
- 충돌 해결 시 추천 DDL과 팀원의 최신 스키마를 함께 유지
- README의 개발 실행 규칙에 따라 기본 `docker-compose.yml`로 전체 재빌드
- DB 볼륨은 삭제하지 않음

### 왜 `docker-compose.local.yml`을 사용하지 않았는가

`docker-compose.local.yml`은 팀원이 전달한 완성 ARM64 이미지를 인터넷 없이 실행하는 용도다. 현재 브랜치의 수정 코드를 반영하려면 로컬 소스를 직접 빌드하는 기본 Compose가 필요하다.

```text
개발 코드 검증
→ docker compose up -d --build

완성 이미지 오프라인 시연
→ docker compose -f docker-compose.local.yml up -d --no-build --pull never
```

### 결과

- 전체 자체 서비스 이미지 빌드 성공
- 모든 컨테이너 실행 성공
- Eureka 등록 후 Gateway 대표 API `200`

## 9. 테스트와 실제 검증 결과

### 9.1 자동 테스트

- recommend-service 자동 테스트 16개: 이전 실행에서 통과
- 프론트 추천 변환 테스트 3개: 현재 다시 실행해 통과
- Vue 프로덕션 빌드: 현재 다시 실행해 통과
- Course·Enrollment·User·Payment Gradle 테스트: 최신 dev 병합 후 통과 기록 보유

현재 로컬 기본 Python에는 `pytest`가 설치돼 있지 않아 이번 문서 갱신 시점에는 백엔드 16개를 다시 실행하지 못했다. 이후 백엔드 소스 변경은 없었지만, 발표 전 테스트 환경을 다시 구성해 한 번 더 실행하는 것이 좋다.

### 9.2 Docker 및 Gateway 검증

```text
전체 Docker 이미지 빌드             성공
MariaDB                              healthy
Kafka                                healthy
Eureka                               healthy
Auth Server                          healthy
Gateway /api/courses                 200
Gateway /api/plans                   200
Gateway 추천 health                  200
```

### 9.3 실제 브라우저 종단 간 시연

```text
LinguaRoute 로그인 버튼
→ Auth Server 로그인
→ Authorization Code 발급
→ /callback에서 Access Token 교환
→ user-service에서 사용자 정보 조회
→ 직원 홈 /app 이동
→ AI 추천 조건 입력
→ Gateway 추천 API 호출
→ 실제 OpenAI 응답
→ AI 추천 결과 화면 표시
→ MariaDB 저장 확인
```

실제 확인한 추천 조건:

```text
언어: 영어
수준: 중급
직무: 글로벌 세일즈
상황: 고객 미팅
목표: 해외 고객에게 제품을 자연스럽게 설명하고 질문에 자신 있게 답하고 싶음
```

DB에서 `source=AI`와 추천 항목·추천 이유가 저장된 것을 확인했다.

## 10. 발표자가 사용할 수 있는 설명

### 10.1 1분 설명

> 저는 AI 강의 추천을 담당하는 recommend-service와 Gateway 통합을 구현했습니다. 직원이 언어, 수준, 직무, 업무 상황과 학습 목표를 입력하면 추천 서비스가 user-service에서 최신 직원 권한을 확인하고, enrollment-service에서 기존 수강 이력을 조회한 뒤, course-service에서 실제 활성 강의 후보를 가져옵니다. OpenAI는 서버가 전달한 후보 안에서 강의와 추천 이유를 생성합니다.
>
> 여기서 AI 결과를 그대로 사용하지 않고 실제 강의 ID, 활성 상태, 요청 언어와 중복 여부를 서버가 다시 검증했습니다. OpenAI 호출이 실패하면 규칙 기반 추천으로 전환해 기능 전체가 중단되지 않도록 했습니다. 내부 API는 Gateway에서 404로 차단하고 서비스 간 호출에서는 내부 API 키를 검사했습니다. 최종적으로 직원 OAuth 로그인부터 실제 OpenAI 추천 결과와 DB 저장까지 종단 간 테스트를 완료했습니다.

### 10.2 30초 설명

> 저는 AI 추천 마이크로서비스와 통합을 담당했습니다. 사용자 권한, 수강 이력과 실제 활성 강의를 각 서비스의 내부 API로 조합하고, OpenAI가 그 후보 안에서 강의와 추천 이유를 생성하도록 했습니다. AI 결과는 서버에서 재검증하고 장애 시 규칙 기반으로 전환했습니다. 실제 직원 로그인부터 OpenAI 추천과 DB 저장까지 시연을 완료했습니다.

### 10.3 기술 차별점 네 가지

1. 다른 서비스 DB를 직접 조인하지 않고 내부 API 계약을 사용했다.
2. LLM 출력을 신뢰하지 않고 실제 강의 데이터와 재검증했다.
3. 외부 AI 장애 시 규칙 기반 fallback으로 사용자 흐름을 유지했다.
4. Gateway 차단과 내부 API 키 검증을 함께 적용했다.

## 11. 발표 예상 질문과 답변

### Q1. 단순 필터링으로도 추천할 수 있는데 왜 AI를 사용했나요?

단순 필터는 언어·수준처럼 정형화된 조건을 정확히 거르는 데 적합하다. AI는 직무, 업무 상황과 자유로운 학습 목표를 함께 해석하고 사용자에게 자연스러운 추천 이유를 설명하는 역할을 맡는다. 실제 강의 존재 여부와 활성 상태는 AI가 아니라 서버가 검증한다.

### Q2. AI가 없는 강의를 만들어내면 어떻게 하나요?

AI에게 전체 강의 생성을 맡기지 않고 course-service에서 조회한 실제 후보를 전달한다. 응답 이후에도 추천 ID를 실제 후보와 다시 대조하고, 존재하지 않는 ID와 중복을 제거한다. 유효한 결과가 없으면 규칙 기반 fallback을 사용한다.

### Q3. 왜 recommend-service가 course DB를 직접 조회하지 않았나요?

MSA에서는 각 서비스가 자신의 데이터를 소유한다. course-service가 강의 상태와 언어 규칙을 책임져야 하며, 추천 서비스가 DB에 직접 접근하면 스키마 변경과 배포가 서로 강하게 결합된다. 그래서 내부 API 계약을 사용했다.

### Q4. OpenAI가 장애 나면 서비스도 사용할 수 없나요?

아니다. 실제 강의 후보를 기반으로 규칙 기반 추천을 반환한다. 응답의 `source` 값과 화면 안내를 통해 AI 추천과 fallback을 구분한다.

### Q5. 자동 테스트에서도 실제 OpenAI를 호출하나요?

호출하지 않는다. 자동 테스트에서는 Provider를 가짜 응답으로 대체해 결과 검증과 fallback 로직을 검사한다. 실제 OpenAI 호출은 비용과 외부 상태의 영향을 받으므로 별도의 수동 통합 시연에서 검증했다.

### Q6. 보안은 어떻게 처리했나요?

외부 요청은 Gateway가 Access Token을 검사한다. 내부 API는 Gateway에서 404로 차단하고, 서비스 간 직접 호출에는 `X-Internal-Api-Key`를 사용한다. 직원 권한은 user-service에서 최신 `businessRole`과 `status`를 다시 조회한다.

### Q7. 왜 수준과 상황이 완전히 일치하지 않는 강의가 추천될 수 있나요?

현재 서버가 반드시 일치하도록 강제하는 조건은 실제 강의 존재, ACTIVE 상태와 언어다. 수준과 상황은 AI가 적합도를 판단한다. 후보가 적으면 인접 수준의 강의를 선택할 수 있다. 향후에는 수준·상황 일치 점수를 강화하거나 후보 조회 단계에서 필터를 추가할 수 있다.

### Q8. 실시간으로 ChatGPT처럼 글자가 나오는 기능도 있나요?

현재는 OpenAI 응답이 완료된 후 추천 설명과 강의 카드를 한 번에 표시한다. 실제 토큰 스트리밍은 추가 고도화 범위다. 구현하려면 OpenAI 스트림을 SSE로 전달하고 프론트가 토큰 이벤트를 누적 표시하도록 확장하면 된다.

## 13. 선택적 고도화 작업

다음 항목은 최초 담당 범위를 완료하기 위한 필수 작업이 아니라 포트폴리오·운영 고도화에 해당한다.

### 13.1 추천 품질 개선

실제 테스트에서 영어 중급·고객 미팅 조건에 영어 고급·임원 발표 강의가 추천됐다. 언어와 ACTIVE 조건은 충족하지만 수준과 상황 적합도는 낮을 수 있다.

개선 방법:

- course-service 후보 조회에서 수준·상황 필터 추가
- 수준 차이에 감점 적용
- 정확히 일치하는 후보를 먼저 정렬
- AI 프롬프트에서 불일치 강의 선택 제한
- 일치 후보가 없을 때만 인접 수준 추천 허용

### 13.2 실제 토큰 스트리밍

```text
추천 조건 제출
→ “등록된 강의를 분석하고 있습니다” 표시
→ OpenAI 설명 토큰을 SSE로 실시간 전달
→ 화면에 문장이 생성되는 과정 표시
→ 설명 완료 후 강의 카드 표시
→ DB 저장
```

이 기능은 사용자에게 AI가 직접 설명하는 느낌을 강화하지만 현재 확정 MVP에는 포함되지 않았다.

### 13.3 운영 보안과 비용 관리

- recommend-service 직접 포트 비공개 또는 자체 JWT 검증
- 개발용 내부 API 키와 DB 비밀번호의 운영환경 fail-fast
- 사용자별 일일 추천 횟수 제한
- IP·사용자 기준 rate limit
- OpenAI 호출 비용과 응답 시간 모니터링
- API 키 교체와 비밀 관리 시스템 적용
- enrollment-service 장애 시 fail-open 정책 재검토

## 16. 마지막으로 기억할 핵심

이 작업의 핵심은 OpenAI API를 한 번 호출한 것이 아니다.

```text
서로 다른 서비스가 소유한 데이터를 API 계약으로 조합하고
→ 최신 사용자 권한을 확인하고
→ 기존 수강 이력을 제외하고
→ 실제 활성 강의만 AI 후보로 제공하고
→ AI 결과를 서버가 다시 검증하고
→ 외부 AI 장애 시 fallback을 제공하고
→ 내부 API를 이중으로 보호하고
→ 실제 로그인부터 DB 저장까지 통합한 것
```

이 흐름을 중심으로 발표하면 AI 추천 담당자이 담당한 `AI 추천·통합` 역할과 MSA를 적용한 이유를 가장 정확하게 설명할 수 있다.
